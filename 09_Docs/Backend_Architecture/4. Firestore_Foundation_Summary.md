# Firestore Foundation Summary

## Purpose
Summarizes the core Firestore setup, indexing, and overall strategy.

## Architectural Decisions
Tenant-isolated hierarchical collections (/schools/{schoolId}/...).

## Implementation Reasoning
The decisions were made to strictly enforce the EduPulse Blueprint requirements. By moving authoritative logic to the backend and tightly securing the Firestore rules, we establish a zero-trust relationship with the frontend payload, guaranteeing data integrity.

## Scalability Considerations
Designed to prevent hot-document write contention using append-only snapshots and asynchronous background orchestration. Avoids O(N) operations in triggers.

## Multi-Tenant Considerations
Strict hierarchical pathing (`/schools/{schoolId}/`) combined with `request.auth.token.schoolId` validation ensures data bleeding is mathematically impossible at the database layer.

## Offline-First Considerations
Client relies on Firestore SDK's local cache and queued writes. Backend strictly enforces `request.time` (Server Timestamps) to correctly reconcile reconnected event storms chronologically.

## Performance Considerations
Minimizes chained trigger cascades to lower latency and invocation costs. Queries are strictly indexed and cursor-paginated.

## Future Extensibility Considerations
Architecture is pre-configured to easily adopt Pub/Sub for heavy background jobs and supports a future `districtId` layer natively in the auth tokens.

## Risks Mitigated
- Leaderboard Manipulation (Frontend tampering blocked).
- Double Point Allocation (Idempotency locks).
- Infinite Trigger Loops (Orchestrator pattern).
- Cross-Tenant Data Leaks (Hard RBAC boundaries).

## Future Migration Readiness
The decoupled orchestration pipeline makes it trivial to migrate specific heavy services (like analytics) to dedicated microservices or Cloud Run in the future.
