## Workflow Explanations
1. Developer runs `npm run dev:emulators`.
2. Emulators boot up, optionally loading cached state from `./emulator_data`.
3. If empty, developer runs `npm run seed:run` which safely injects multi-tenant entities.
4. Validation script ensures claims and database are synchronized.

## Testing Strategy
The stabilization phase prioritizes deterministic testing. The `runSeeds.ts` ensures that UI developers can write tests against known states (e.g., student_1 always has 120 points). Integration tests for cloud functions heavily utilize `firebase-functions-test` wrapping emulator states.

## Emulator Setup
Configured via `firebase.json`: Auth (9099), Firestore (8080), Functions (5001), UI (4000).

## RBAC Considerations
All personas are seeded with strict `schoolId` values. Role hierarchies (super_admin vs principal vs teacher) are embedded into tokens directly.

## Multi-Tenant Considerations
Seeding introduces `school_2` alongside `school_1` explicitly to validate that no queries accidentally bleed records across tenants.

## Scalability Considerations
Seed generation uses Firestore `batch()` limits (max 500) carefully to avoid memory timeouts. Local testing supports thousands of nodes.

## Security Considerations
**CRITICAL**: All seed scripts include a fatal kill-switch. If `FIRESTORE_EMULATOR_HOST` is missing, process exits with code 1. It is mathematically impossible to execute `runSeeds.ts` against the live production database.

## Future Extensibility Considerations
The modular seeder pattern allows new modules (like Gamification or Analytics) to append their own Seeder files to `runSeeds.ts` effortlessly.
