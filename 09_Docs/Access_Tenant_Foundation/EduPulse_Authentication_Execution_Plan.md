# Phase 1B: Authentication Execution Plan

## Purpose
This document defines the comprehensive execution plan for implementing Phase 1B — Authentication. It details the domain architecture, data layer integrations, runtime flows, and security considerations required to securely authenticate users before resolving their `TenantContext`.

---

## 1. Authentication Domain Architecture

The Domain Layer remains strictly isolated from Firebase dependencies.

### AuthUserEntity
Represents the authenticated identity, separate from the full user profile (which is handled in Phase 1E).
- `uid`: Unique identifier.
- `email`: User's email address.
- `emailVerified`: Boolean status.
- `providerId`: e.g., 'password', 'google.com'.

### AuthenticationState
Defines the explicit runtime stages for the Authentication routing and observability:
- `unauthenticated`
- `authenticating`
- `authenticated`
- `resolvingTenantContext`
- `pendingPasswordChange`
- `locked`
- `suspended`
- `failure`

### AuthenticationFailure Models
Domain-safe exception classes mapped from underlying data layer errors:
- `InvalidCredentialsFailure`
- `UserDisabledFailure`
- `UserNotFoundFailure`
- `NetworkFailure`
- `UnknownAuthFailure`

---

## 2. Authentication Data Layer

The Data Layer integrates directly with the chosen authentication provider.

### AuthenticationDatasource
An abstract interface defining the core authentication contract:
- `signInWithEmailAndPassword(email, password)`
- `signInWithGoogle()`
- `signOut()`
- `sendPasswordResetEmail(email)`
- `updatePassword(newPassword)`
- `Stream<AuthUserEntity?> get authStateChanges`

### Firebase Authentication Integration
`FirebaseAuthDatasourceImpl` implements the `AuthenticationDatasource` using the `firebase_auth` SDK. It executes the raw calls and throws Firebase-specific exceptions.

### AuthenticationRepository
`AuthRepositoryImpl` wraps the datasource. Its primary responsibilities are:
- Orchestrating login/logout requests.
- Catching `FirebaseAuthException` and mapping it to the domain-safe `AuthenticationFailure` models (via an `AuthExceptionMapper`).
- Exposing the `Stream<AuthUserEntity?>` to the application layer.

## 3. Supported Providers

### V1 Supported Providers
- **Email + Password**: The primary method for staff and parents.
- **Google Sign-In**: Supported for convenience and federated identity.

### Future Providers (Not Implemented in V1)
The architecture is designed to support future additions without structural changes:
- Phone OTP
- Apple Sign-In
- Microsoft Login

## 4. User State Handling

The application must respond appropriately to the following user states during the authentication flow:

- **Created**: The user account exists in Firebase, but the user has never logged in.
- **PendingPasswordChange**: The user has logged in using a system-generated temporary password. The runtime must route them to a "Force Password Change" screen before granting access.
- **Active**: Normal operating state.
- **Locked**: Too many failed login attempts. Managed via Firebase's native rate-limiting and custom Firestore flags.
- **Suspended**: The user account is administratively disabled. `FirebaseAuth` rejects login.
- **Archived**: Soft-deleted users are treated as Suspended at the authentication level.

---

## 5. Session Management

### Mobile (Persistent Session)
- **Behavior**: Users remain perpetually logged in.
- **Termination**: Session ends only upon explicit logout, password change, or administrative account/school suspension.

### Web (60 Minute Idle Timeout)
- **Behavior**: An idle timer tracks user interaction (mouse movement, clicks, keyboard).
- **Termination**: After 60 minutes of inactivity, the session is forcibly expired, the token is cleared locally, and the user is routed to the login screen.

---

## 6. Password Management

- **Admin Reset**: A School Admin can trigger a password reset email or manually generate a new temporary password for a user.
- **Email Reset**: Users can self-serve password recovery via the "Forgot Password" flow.
- **Temporary Password**: Generated by the system during teacher onboarding.
- **Forced Password Change**: A flag `requiresPasswordChange` stored inside the user document at `schools/{schoolId}/users/{uid}` forces the UI to block dashboard access. **Note: This value must NOT be stored inside Firebase Custom Claims**, to allow easier administration and support operations.

---

## 7. Authentication Runtime Flow

### Login Flow
1. User submits credentials.
2. `AuthRepository` validates against Firebase.
3. `auth_state_changes` emits the `AuthUserEntity`.
4. State transitions to `resolvingTenantContext`.
5. System checks `schools/{schoolId}/users/{uid}` for `requiresPasswordChange`.
6. System checks for Google Sign-In user existence (see Section 10).
7. System triggers TenantContext integration (see Section 8).
8. State transitions to `authenticated` and routing delegates to Dashboard.

### Session Restore
1. App launches.
2. `auth_state_changes` immediately emits the cached `AuthUserEntity`.
3. State transitions to `resolvingTenantContext`.
4. System triggers TenantContext integration.
5. Routing delegates to Dashboard.

### Logout
1. Triggered explicitly by the user or implicitly (idle timeout).
2. `AuthRepository.signOut()` executes.
3. `TenantContextResolver.clearContext()` executes.
4. UI is forcibly routed to the Login screen.

---

## 8. TenantContext Integration & Suspension

Authentication is only the first half of the runtime access flow. It must integrate flawlessly with Phase 1A.

```text
Authentication Success (uid established)
        ↓
TenantContext Resolution (resolvingTenantContext state)
        ↓
Access Validation
        ↓
Application Access (authenticated state)
```

### School Suspension Flow
If the user's School is marked as `Suspended`, the `TenantContextResolver` will refuse initialization.
**CRITICAL**: Do NOT force a Firebase Logout. The user remains authenticated. Access is blocked purely by TenantContext, resulting in:
```text
School Suspended -> Suspension Screen
```

---

## 9. Multi-Device Support

- **Simultaneous Sessions**: Users may log in across Desktop, Mobile, and Tablet concurrently.
- **Global Invalidation**: Critical security events (like a Password Reset or Account Suspension) will automatically revoke all active refresh tokens via Firebase.
- **Real-time Logout**: The `auth_state_changes` stream on each device will instantly detect the token revocation and forcibly log the user out across all active devices.

---

## 10. Security Considerations

### Google Sign-In User Validation
Google Sign-In must **NOT** automatically create accounts. The flow must be:
```text
Google Sign-In -> Email Lookup -> Existing EduPulse User? -> Allow Login
```
If the user does not exist in EduPulse, login fails. User creation remains strictly School Admin Controlled.

### Additional Protections
- **Failed Login Protection**: Relies on Firebase Authentication's native brute-force protection.
- **Account Locking**: Repeated failures trigger temporary Firebase locks.
- **Session Invalidation**: Changing passwords automatically rotates tokens.

---

## 11. Authentication Audit Events

The Authentication phase must generate audit events for critical access operations. These events must be written to:
`schools/{schoolId}/auditLogs`

Supported events:
- `Login Success`
- `Login Failure`
- `Logout`
- `Password Reset Requested`
- `Password Changed`
- `Account Locked`
- `Account Unlocked`
- `Forced Logout`

*Note: If the Audit Module is not yet fully available, this implementation may be stubbed, but the event contract must be fully defined.*

## 12. Testing Strategy

### Unit Tests
- Test `AuthExceptionMapper` to ensure all Firebase errors convert correctly to `AuthenticationFailure` variants.
- Test `AuthUserEntity` serialization and equality.

### Repository Tests
- Use `mocktail` to mock `AuthenticationDatasource`.
- Verify `AuthRepositoryImpl` correctly maps errors and emits the proper `AuthUserEntity`.

### Authentication Flow & Validation Tests
- **Web Idle Timeout Test**: Verify 60 Minutes Inactive -> Session Expired.
- **School Suspension Test**: Verify School Suspended -> Suspension Screen (without forcing Firebase logout).
- **Multi-Device Session Revocation Test**: Verify Password Reset -> All Active Sessions Invalidated on Desktop, Mobile, and Tablet.
